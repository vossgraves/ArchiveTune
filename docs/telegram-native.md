# The Telegram engine (TDLight)

## Why the native library is not in the APK

`libtdjni.so` is 21.7 MB for arm64-v8a and 24.3 MB for x86_64. Packaged for both, DEFLATE-compressed,
that was **17.3 MiB of a 42.0 MiB universal APK** — 41% of the download — paid by every user for an
optional integration most never sign in to.

It is now downloaded on first Telegram use instead: one gzip-compressed, digest-pinned file for the
device's own ABI, about 9.6 MB on arm64. `-PslimTdlib=false` bundles it instead, but you must place
`libtdjni.so` under `app/src/main/jniLibs/<abi>/` yourself — there is no Maven artifact to take it
from any more.

## Why TDLight rather than tdlibx

`com.github.tdlibx:td` shipped the natives for all four ABIs inside its AAR, which is convenient and
is exactly what made the APK fat. TDLight (tdlight-team/tdlight) publishes a leaner build — TDLib
1.8.66 base, static OpenSSL, `-Oz` with thin LTO, stripped — and 4nx3b already builds and hosts it
per-ABI as `.so.gz`.

The trade is that TDLight has no Maven artifact, so `org.drinkless.tdlib.Client` and `TdApi` are
vendored under `app/src/main/java`, generated by the same TDLight commit that built the native
library. That coupling is the point: the Java TL schema can never drift from the `.so`.

## Where the download comes from, and why that is safe

`TDLIB_NATIVE_BASE_URL` defaults to 4nx3b's `tdlight-2b51b33` release. Downloading a native binary
from an upstream repo is only acceptable because `DIGESTS` in `TdLibNativeLibrary` pins the SHA-256
of every ABI's **decompressed** library. A changed or substituted asset fails the check and is
discarded, so the host is untrusted by construction.

Point `-PtdlibNativeBaseUrl=` at your own release to stop depending on upstream hosting; the assets
must be named `libtdjni-<abi>.so.gz` and match the pinned digests.

## Schema differences from TDLib 1.8.56

The 1.8.66 bump changed three calls the fork uses:

| Call | 1.8.56 | 1.8.66 |
|---|---|---|
| `JoinChatByInviteLink` | returned `Chat` | returns `ChatJoinResult` — only `ChatJoinResultSuccess` carries a `chatId`; the other three mean request-sent, bot-approval-required or declined |
| `SearchPublicChats` | `(query)` | `(query, SearchChatTypeFilter)` |
| `SearchChats` | `(query, limit)` | `(query, SearchChatTypeFilter, limit)` |

`null` as the type filter keeps the old "any chat type" behaviour.

## Bumping the TDLight version

1. Take `Client.java` and `TdApi.java` from the release's assets and replace the vendored copies.
2. Update `VERSION` and `DIGESTS` in `TdLibNativeLibrary` from the release's `libtdjni-digests.txt`.
3. Compile. The generated `TdApi` is the only thing that reports schema drift, so a clean compile is
   the check that the binding and the native library agree.
